# Архитектура

Historical Bloodlines — преобразователь Excel-книг в генеалогические схемы.
Telegram-бот — основной способ использования, CLI и Rich launcher —
альтернативные интерфейсы над общим application layer.

## Точки входа и общий сценарий

| Интерфейс | Точка входа | Поведение |
| --- | --- | --- |
| Telegram | `presentation/telegram/bot.py` | Авторизация, загрузка книги, генерация комплекта, отправка и очистка |
| CLI | `cli.py`, команда `bloodlines` | Один запуск с путями, форматом и YAML |
| Launcher | `presentation/launcher/app.py` | Интерактивное меню над тем же builder |

Пути в таблицах приведены относительно `src/historical_bloodlines/`.
`BuildGenealogyUseCase` в `application/services/build_genealogy.py`
принимает инфраструктурные зависимости через конструктор. Он организует
следующие этапы:

1. `ExcelGenealogyReader` читает книгу в `GenealogySheetDTO` и `RawGenealogyRowDTO`.
2. `GenealogyRowParser` нормализует строки в `ParsedGenealogyRowDTO`.
3. `GenealogyAssembler` и `PersonReferenceResolver` строят `Genealogy`.
4. `NetworkXGenealogyValidator` проверяет родительский граф.
5. `GraphvizGenealogyRenderer` вычисляет геометрию, проверяет линии и пишет файл.
6. Для PDF `PdfBookComposer` масштабирует и объединяет страницы.

`BuildResult` содержит путь результата и предупреждения. Для PDF путь указывает
на файл, для SVG/PNG/EPS — на каталог отдельных изображений.

## DTO и модель данных

`RawGenealogyRowDTO` хранит значения Excel почти без интерпретации. Поля
`children_raw`, `spouses_raw`, `generation_raw`, `note_raw` ещё не являются
отношениями или подсказками domain-модели.

`GenealogySheetDTO` разделяет техническое имя листа `name`, отображаемый заголовок
`display_title` и строки `rows`. `PersonReferenceDTO` хранит разобранную ссылку:
имя, уточнение, маркер порядка и исходный текст. Parser не решает, на какого
именно человека она указывает.

| Объект domain | Роль |
| --- | --- |
| `SourcePersonKey` | Техническое имя листа и номер человека; основа UUIDv5 |
| `Person` | Собственные атрибуты человека, без вложенных объектов детей/супругов |
| `PersonLayoutHint` | Необязательные поколение и порядок |
| `MarriageRelation` | Союз двух людей |
| `ParentChildRelation` | Направленный факт родитель → ребёнок |
| `FamilyChildRelation` | Набор родителей, от которого выходит ветвь ребёнка |
| `Genealogy` | Люди по UUID, отдельные множества отношений и предупреждения |

Идентичность не зависит от имени: одноимённые люди могут существовать отдельно.
Связи хранят UUID, поэтому человек не дублируется для нескольких браков и
не возникает циклического графа вложенных Python-объектов.

## Parser, assembler и resolver

Parser очищает текст, разбивает списки по `;` и переносам, читает маркеры
`1)`, уточнения, титулы, согласованные периоды правления и положительные
числа подсказок. Пустые позиции в списке конечных годов могут обозначать
открытый период. Он не ищет людей и не создаёт связи.

Assembler сначала создаёт всех людей, затем разрешает браки и детей.
Поэтому ссылка может указывать на строку ниже. Resolver сравнивает имя,
уточнение, титулы и семейный контекст. Неразрешённая терминальная ссылка
может стать placeholder с предупреждением. Для конкретного ребёнка отдельно
хранятся факт родства и визуальный семейный источник: дети не присоединяются
автоматически ко всем бракам родителя.

NetworkX используется для графовых вычислений и проверки циклов. Его
представление производно от `Genealogy`, а не отдельный источник данных.

## Активный renderer и геометрия

Публичный импорт `historical_bloodlines.infrastructure.graph.GraphvizGenealogyRenderer`
экспортируется из **`readable_renderer.py`**. Файл `renderer.py` содержит базовый
renderer, от которого наследуется активный. Изменение только старых констант
в базовом классе не заменяет версионированную конфигурацию активного renderer.

| Модуль в `infrastructure/graph/` | Ответственность |
| --- | --- |
| `labels.py` и formatter в `readable_renderer.py` | Измерение подписей, переносы, Roboto / Roboto Medium |
| `layout.py`, `orthogonal_layout.py` | Компоненты супругов, поколения и размещение |
| `constraint_solver.py` | Совместное решение ограничений координат |
| `planar_readable_layout.py` | Топологическая корректировка порядка и ограниченный поиск маршрутов |
| `connector_routing.py` | Ортогональные маршруты, препятствия и конфликты |
| `readable_renderer.py` | Сборка геометрии, брачные соединения, проверка, экспорт |

Супруги образуют горизонтальные компоненты; один человек может участвовать
в нескольких союзах. Для несоседних супругов используются дополнительные
маршруты, а ось детей привязана к нужному брачному знаку. Явные поколения и
порядок учитываются как ограничения. Непронумерованные компоненты могут
переставляться с учётом топологии, сохраняя заданный относительный порядок.

Проверки выполняются до записи Graphviz-артефакта. Если маршрут пересекает
подписи или создаёт запрещённый конфликт семейных линий и поиск не находит
решение, генерация завершается ошибкой. Конфиг оформления эту проверку не
отключает.

Graphviz получает заранее рассчитанные позиции и сегменты. `neato -n2`
используется как backend вывода, а не как самостоятельный алгоритм размещения.

## Форматы вывода

- PDF: нативная страница на каждый лист, затем равномерное масштабирование
  на A5/A4 landscape и объединение через `pypdf`. Увеличение ограничено `1.22`.
- SVG/PNG: отдельный файл на каждый лист в каталоге, образованном из stem
  выходного пути.
- EPS: промежуточный `svg:cairo` с контурами текста, затем CairoSVG → EPS.
  Рядом создаётся PNG-превью отдельным рендером.

Прямая legacy PostScript-типографика Graphviz для издательского EPS не
используется: контуры сохраняют вид кириллицы и римских цифр при импорте.

## Жизненный цикл настроек и задания бота

`config/render.py` загружает и проверяет YAML в неизменяемые dataclass-объекты.
Каждый builder получает отдельный `RenderConfig`; настройки не меняют
глобальные классовые параметры других заданий.

`TelegramGenerationService` создаёт builder **на книгу**, а затем использует
его для EPS/PNG и PDF. Это позволяет перечитывать `data/render.yaml` между
заданиями и сохранять единый стиль внутри комплекта. Если builder явно
передан в сервис через конструктор, сервис использует именно его.

Aiogram получает обновления через polling. Проверяются allowlist, расширение
и объявленный размер документа. Загрузка идёт во временный каталог задания,
а рендер — через `asyncio.to_thread` под процессным семафором. После создания
PDF и ZIP бот отправляет их в Telegram, затем временный каталог удаляется.
Семафор ограничивает только один процесс; постоянной очереди заданий нет.

## Хранение и окружение

Excel — постоянный источник генеалогических данных. `Genealogy`, NetworkX-граф
и промежуточные документы живут в памяти/временных каталогах одного запуска.
Сервер не требует БД. Наличие нескольких пользователей бота само по себе
не добавляет постоянное хранение или совместное редактирование книги.

Compose запускает `bot` и разовый `renderer` из общего образа. `./data`
монтируется в `/data`, UID/GID совпадают с владельцем checkout. Опциональный
`proxy` использует sing-box или Xray через overlay-файл. HTTP-сервер и
опубликованные порты этому сценарию не нужны.

Пользовательские инструкции: [бот](telegram-bot.md), [CLI](local-run.md),
[YAML](render-configuration.md). Проверки и развитие: [разработка](development.md).
